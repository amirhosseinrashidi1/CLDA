# Carry Look-Ahead Decimal Adder (CLDA) — Python Simulator


A graphical Python-based simulation and visualization environment for a **Carry Look-Ahead Decimal Adder (CLDA)** based on the architecture and concepts presented in the research paper:

> **Design and Implementation of High-Speed Carry Look-Ahead Decimal Adder (CLDA) Using CMOS Technology**
> IEEE Access, 2025
> DOI: 10.1109/ACCESS.2025.3540836

This project provides a software-level implementation and visual testbench for studying **BCD addition, carry generation, carry look-ahead logic, BCD correction, signal propagation, and CLDA/RCA performance estimation**.

> **Important:** This project is a software-level educational and analytical implementation inspired by the referenced research. It is **not a transistor-level CMOS implementation** and does not reproduce the LT-SPICE simulations or transistor-level schematics presented in the paper.

---

## 1. Project Overview

Decimal arithmetic is important in applications such as financial systems, accounting, banking, databases, and other human-centric computing systems. Binary arithmetic can be used to process decimal values, but direct decimal representations such as **Binary-Coded Decimal (BCD)** can be useful when exact decimal digit representation is required.

A conventional multi-digit BCD adder can be constructed by cascading individual BCD adders using a **Ripple Carry Decimal Adder (RCDA)** structure. In this architecture, the carry generated by one decimal digit must propagate to the following digit, increasing the propagation delay as the operand size grows.

The referenced paper investigates the use of **Carry Look-Ahead (CLA)** techniques to reduce this carry propagation problem and proposes two CMOS-based architectures:

* **CLDA1 — Carry Look-Ahead Decimal Adder 1**
* **CLDA2 — Carry Look-Ahead Decimal Adder 2**

The proposed architectures are investigated for 1-, 2-, 3-, and 4-digit decimal operands and are evaluated using a 45 nm CMOS technology library and LT-SPICE.

This project translates the main computational concepts into an interactive Python environment that allows the user to observe and analyze the operation of a decimal adder.

# 3. Theoretical Background

## 3.1 Binary-Coded Decimal (BCD)

BCD represents every decimal digit using four binary bits.

For example:

| Decimal |   BCD  |
| ------: | :----: |
|       0 | `0000` |
|       1 | `0001` |
|       2 | `0010` |
|       5 | `0101` |
|       9 | `1001` |

A decimal digit therefore occupies one 4-bit BCD group.

The paper describes a conventional BCD adder as a circuit that accepts two BCD digits and a carry input and produces a BCD digit together with a carry output.

---

## 3.2 BCD Correction

The binary addition of two valid BCD digits can produce values greater than 9.

For example:

```text
  8
+ 7
---
 15
```

Since `15` cannot be represented as a single valid BCD digit, a correction of `6` is required:

```text
15 + 6 = 21
```

The lower four bits represent the BCD result and the generated carry is propagated to the next decimal digit.

The referenced paper describes this conventional correction mechanism as adding `0110` (decimal 6) whenever the intermediate result exceeds decimal 9.

The Python implementation follows this conceptual BCD correction process when calculating each decimal digit.

---

# 4. Ripple Carry vs. Carry Look-Ahead

## Ripple Carry Decimal Adder

In an RCDA, the carry output of one BCD digit becomes the carry input of the next digit.

Conceptually:

```text
Digit 0
   │
   ▼
Digit 1
   │
   ▼
Digit 2
   │
   ▼
Digit 3
```

Therefore, the carry signal may need to traverse multiple decimal stages.

The referenced paper identifies this propagation chain as a major source of delay in multi-digit BCD addition.

---

## Carry Look-Ahead Decimal Adder

The CLDA approach attempts to reduce this dependency by calculating carry signals using the input information rather than waiting for the previous carry to ripple through every stage.

Conceptually:

```text
             ┌───────────────┐
A ──────────►│               │
B ──────────►│ Carry Look    │──► C1
Cin ────────►│ Ahead Logic   │──► C2
             │               │──► C3
             └───────────────┘   ──► C4
```

The paper moves carry computation into dedicated CLA logic units so that carry outputs can be determined without the conventional ripple dependency.

The paper develops two versions of this architecture:

```text
CLDA1
CLDA2
```

and provides Boolean equations and CMOS realizations for both.

# 7. Carry Look-Ahead Logic

The implementation contains a dedicated function for generating carry-related signals:

```python
generate_cla_carry()
```

The function calculates:

* Generate bits (`G`)
* Propagate bits (`P`)
* Intermediate carry signals
* Carry-out
* Digit Generate
* Digit Propagate

The carry equations are explicitly calculated rather than relying only on Python's built-in integer addition.

This makes the implementation useful for studying the internal logic of carry computation.

# 14. Verification

The application performs an independent verification step.

After calculating the BCD result, the software:

1. Decodes the generated BCD digits.
2. Converts the result to decimal.
3. Calculates the reference result using Python integer arithmetic.
4. Compares both results.
5. Reports whether the results match.

Conceptually:

```text
BCD Result
    │
    ▼
BCD Decode
    │
    ▼
Decimal Result
    │
    ├──────────────┐
    │              │
    ▼              ▼
BCD Calculation   Python Reference
    │              │
    └──────┬───────┘
           ▼
       Verification
```

This verification mechanism is implemented in `analyze_bcd()`.

# 22. Why CLDA?

The main motivation for using Carry Look-Ahead is to reduce the dependency of higher-order carries on lower-order carry propagation.

The paper explains that conventional ripple carry structures suffer from increasing delay as the number of BCD digits increases, while CLA techniques break the conventional carry chain by computing carries from input-related signals.

However, Carry Look-Ahead also introduces additional hardware complexity. The research therefore limits the proposed CLDA structures to up to four digits and suggests combining smaller CLDA blocks for larger operands.
